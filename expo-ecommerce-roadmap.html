Bu rehber nasıl kullanılır

Bu bir kitap değil, bir çalışma sırası. Her faz bir öncekinin ürettiği dosyaları kullanır ve sadece onları kullanır. Bir fazı atlarsan, sonraki fazda var olmayan bir dosyayı import etmeye çalışırsın.

Tüm fazlar aynı altı bölümden oluşur. Bu tekrar bilinçli: bir süre sonra yeni bir özelliği hangi sırayla yazacağını ezberlemeden bilirsin.

Şu an tam olarak buradasın

M5'in ortasındasın. Ana sayfayı (M6) bitirebilmen için önce M5'teki ortak parçaları yazman gerekiyor. Ama ondan önce, mevcut kodda düzeltilmesi gereken dört şey var — bunlar aynı zamanda rehberin ilk üç bölümünün pratiği.

Düzeltme 1 — /api/home dizi döndürmüyor hata

src/app/(tabs)/index.tsx içinde tip HomeDto[] yazılmış. Sözleşmeye göre bu endpoint tek bir nesne döndürüyor:

// src/types/api.ts (uretilmis dosya, satir ~3637)
HomeDto: {
    bestsellers: components["schemas"]["ProductListDto"][];
    newArrivals: components["schemas"]["ProductListDto"][];
    discounted:  components["schemas"]["ProductListDto"][];
};

Yani data.bestsellers diyeceksin, data[0].bestsellers değil. Bu yüzden yorum satırına aldığın const { bestsellers, newArrivals, discounted } = data; satırı çalışmıyordu: tip dizi olduğu için TypeScript o alanları bulamıyordu (ve data ilk render'da undefined olduğu için doğrudan destructuring de çökerdi).

Düzeltme 2 — Tab etiketleri hata

src/app/(tabs)/_layout.tsx içinde üç sekmenin etiketi de "Sepetim": cart, favorites ve account. İkisi "Favorilerim" ve "Hesabım" olmalı. Kopyala-yapıştır sonrası en kolay gözden kaçan hata türü budur.

Düzeltme 3 — Ekranın içinde useQuery mimari

src/app/(tabs)/index.tsx, useQuery'yi ve apiRequest'i doğrudan ekranın içinde çağırıyor. M4'te kurduğun katman kuralı tam olarak bunu engellemek içindi. Nedenini ve doğrusunu bir sonraki bölümde ayrıntılı anlatıyorum; düzeltmeyi M6'da yapacaksın.

Düzeltme 4 — getProducts elle yazılmış tip döndürüyor

src/lib/api/product.ts içinde dönüş tipi { items: ProductListDto[]; totalCount: number } olarak elle yazılmış. Sözleşmede bunun hazır bir karşılığı var ve daha fazla alan içeriyor:

Mimari sözleşme — kod nereye yazılır

Bu bölüm rehberin kalbi. Sorduğun "UI component'i yazarken nerede useQuery kullanmalıyım, nerede hook yazmalıyım, ekranlarda neye dikkat etmeliyim" sorusunun cevabı burada. Fazlara geçmeden önce bunu bir kez okumak, sonraki 20 fazda kendi kendine karar verebilmeni sağlar.

Verinin akışı

Bir ürün listesinin ekrana gelmesi, her zaman aynı beş durakta ilerler. Yeni bir özellik yazarken de aynı sırayla yazarsın — aşağıdan yukarı.

Ekran src/app/(tabs)/index.tsx | useHome() cagirir, durumlari yerlestirir v Hook src/hooks/use-home.ts | queryKey + queryFn eslestirir, cache'i yonetir v API fonksiyonu src/lib/api/home.ts | path'i ve query string'i kurar, donus tipini soyler v Client src/lib/api/client.ts | base URL, header, token, 401 -> refresh, hata normalizasyonu v HTTP Commerce.Api

Yazma sırası kuralı: Yeni bir özelliğe her zaman en alttan başla. Önce API fonksiyonu, sonra query key, sonra hook, en son ekran. Böylece ekranı yazarken elinde çalışan ve tipli bir veri kaynağı olur; "önce UI yapayım sonra bağlarım" yaklaşımının yarattığı yeniden yazma işi ortadan kalkar.

Karar ağacı: bu kodu nereye koyayım?

Bir kod parçası yazarken takıldığında bu sorularımı yukarıdan aşağı uygula. İlk "evet" cevabı, dosyanın yerini söyler.

Yazdigin sey fetch/URL/header iceriyor mu? evet -> src/lib/api/<alan>.ts (React yok, hook yok) hayir | v useQuery / useMutation / useInfiniteQuery iceriyor mu? evet -> src/hooks/use-<sey>.ts (ekranda ASLA) hayir | v React'siz calisan saf bir donusum mu? (fiyat formati, tarih, hesap) evet -> src/lib/utils/<ad>.ts hayir | v Ekranda gorunen bir parca mi ve birden fazla yerde kullanilabilir mi? evet -> src/components/... hayir | v Sunucudan gelmeyen, uygulama genelinde paylasilan bir state mi? evet -> src/stores/<ad>-store.ts (Zustand, M12) hayir | v Geriye kalan: src/app/... icindeki ekran dosyasi (yerlesim, kosullu render, navigasyon)

useQuery ekranda mı, hook'ta mı?

Cevap: her zaman hook'ta. İstisnasız. Şu an src/app/(tabs)/index.tsx bu kuralı çiğniyor, o yüzden en iyi örnek o.

Şu an ne var

// src/app/(tabs)/index.tsx  — ekranin ICINDE query
export default function Index() {
  const { data, isLoading, isError, refetch, isRefetching } = useQuery({
    queryKey: queryKeys.home,
    queryFn: () => apiRequest<components["schemas"]["HomeDto"][]>(`/api/home`),
  });
  // ...
}

Ne olmalı

// 1) src/lib/api/home.ts — sadece HTTP
import type { components } from "@/types/api";
import { apiRequest } from "./client";

export type HomeDto = components["schemas"]["HomeDto"];

export function getHome() {
  return apiRequest<HomeDto>("/api/home");
}

// 2) src/hooks/use-home.ts — sadece cache/query
import { useQuery } from "@tanstack/react-query";
import { getHome } from "@/lib/api/home";
import { queryKeys } from "@/lib/api/query-keys";

export function useHome() {
  return useQuery({ queryKey: queryKeys.home, queryFn: getHome });
}

// 3) src/app/(tabs)/index.tsx — sadece ekran
export default function Index() {
  const { data, isLoading, isError, refetch, isRefetching } = useHome();
  // ...
}

Neden? Dört somut sebep — hepsi bu projede gerçekten başına gelecek:

  • Aynı veri ikinci ekranda lazım olduğunda. "Öne çıkan ürünler"i yarın kategori ekranının altında da göstermek istersen, hook varsa tek satır: useHome(). Hook yoksa queryKey'i, queryFn'i ve tipi kopyalarsın; birini güncellemeyi unutunca iki ekran farklı veri gösterir.
  • Query key tek yerde kalır. Key'i ekranda yazarsan, mutation sonrası invalidateQueries çağıracağın yerde key'in aynısını tekrar yazman gerekir. Bir harf farkı = cache hiç temizlenmez ve hata da vermez. Sessiz hatalar, gürültülü hatalardan çok daha pahalıdır.
  • Ekran, API'nin şeklinden bağımsız kalır. Backend /api/home'u ikiye bölerse sadece hook değişir; ekran dosyasına dokunmazsın.
  • Fetch mantığını tek yerden zenginleştirirsin. Yarın staleTime, select, placeholderData eklemek istediğinde tek dosyayı açarsın.

"Ama bu query sadece tek bir ekranda kullanılıyor"

Yine de hook yaz. Maliyeti altı satır; getirisi, altı ay sonra o veriye ikinci bir yerden ihtiyaç duyduğunda hiçbir şeyi taşımak zorunda kalmaman. Kuralın istisnası olmaması, kuralı düşünmeyi bırakmanı sağlar — asıl kazanç bu.

Aynı hook'u beş component'te çağırmak beş istek atar mı?

Hayır. Yeni başlayanların en çok yanıldığı nokta bu, ve bu yanılgı yüzünden gereksiz prop drilling yapılır.

TanStack Query, veriyi queryKey'e göre tek bir cache'te tutar. Aynı key ile aynı anda kaç component useCart() çağırırsa çağırsın:

  • Ağa tek istek gider (buna deduplication denir).
  • Hepsi aynı veriyi, aynı anda, aynı isLoading durumuyla görür.
  • Veri değişince hepsi birlikte güncellenir.
  • Veri staleTime içindeyse (senin ayarında 30 saniye) yeniden istek bile atılmaz.

Bu yüzden şu tercihi rahatça yapabilirsin:

// Sepet rozetini gostermek icin sepeti ta yukaridan prop olarak gecirmene gerek yok:
// tab layout'unda dogrudan hook'u cagir.
function CartBadge() {
  const { data } = useCart();          // ayni cache, ek istek yok
  const count = Number(data?.totalQuantity ?? 0);
  return count > 0 ? <Badge>{count}</Badge> : null;
}

Üç component tipi

"Component'e prop mu geçeyim, içeride hook mu çağırayım?" sorusunun cevabı, yazdığın şeyin hangi tip olduğuna bağlı. Bu projede üç tip var:

TipÖrnekVeriyi nasıl alırKural
1. Gösterim (dumb) ProductCard, PriceBlock, Button, EmptyState Sadece prop. İçinde useQuery/useMutation olmaz. API'den haberi olmaz. Böylece ana sayfada, arama sonuçlarında, favorilerde aynı component çalışır.
2. Bağlı (connected) FavoriteButton, AddToCartButton, CartBadge Kendi hook'unu içeride çağırır; dışarıdan sadece productId gibi bir kimlik alır. Kendi aksiyonunu ve o aksiyonun loading/hata durumunu kendi taşır.
3. Ekran src/app/** altındaki her dosya Hook'ları çağırır, durumları yönetir, yerleşimi kurar. İçinde iş mantığı olmaz; "hangi durumda ne gösterilir" kararını verir.

Bağlı component ne zaman doğru seçim?

Ölçüt basit: Aksiyon her yerde aynıysa, aksiyonu component'in içine koy.

Kalp ikonuna basmak; ana sayfada, ürün listesinde, ürün detayında, arama sonuçlarında ve favoriler ekranında tamamen aynı şeyi yapar: favoriye ekle/çıkar, sonra iki query'yi invalidate et. Bunu ekranlara dağıtırsan aynı mutation'ı beş kez yazarsın. Bu yüzden FavoriteButton kendi mutation'ını taşır:

// components/product/favorite-button.tsx  (M14'te tamamlanacak hali)
export function FavoriteButton({ productId }: { productId: number }) {
  const { isFavorite, toggle, isPending } = useFavoriteToggle(productId); // hook icerde
  return (
    <Pressable onPress={toggle} disabled={isPending} hitSlop={8}>
      <Ionicons name={isFavorite ? "heart" : "heart-outline"} size={22} />
    </Pressable>
  );
}

// Kullanimi her yerde ayni ve tek satir:
<FavoriteButton productId={product.id} />

Buna karşılık ProductCard gösterim component'idir: ürünü prop olarak alır, hiçbir şey çekmez. İçinde bir FavoriteButton barındırması bu kuralı bozmaz — kart hâlâ API'yi tanımıyor, sadece kendi kendine yeten bir çocuk component'i yerleştiriyor.

Pratik eşik: Bir veriyi prop olarak ikiden fazla seviye aşağı taşıyorsan ya da aynı veriyi üç kardeş component istiyorsa, prop'u bırak ve hook'u ihtiyaç duyulan yerde çağır. Cache zaten tekilleştiriyor (yukarıdaki bölüm), yani "performans için prop geçeyim" gerekçesi burada geçerli değil.

Hangi state nereye?

"State" tek bir şey değil. Dört farklı türü var ve her birinin doğru evi farklı. Yanlış eve koymak, bu projedeki en pahalı hatadır (özellikle sepette).

State türüÖrnekNerede dururNeden
Sunucu state Ürünler, sepet, siparişler, favoriler, kullanıcı bilgisi TanStack Query (src/hooks/) Gerçek kaynağı sunucu. Kopyasını client'ta tutarsan senkron kaybedersin.
Form state Login/adres/checkout alanları, hata mesajları React Hook Form (M11) Her tuş vuruşunda tüm ekranı yeniden render etmeden yönetir.
Geçici UI state Modal açık mı, aktif carousel index'i, arama kutusundaki metin useState — component'in kendi içinde Kimseyi ilgilendirmiyor; global yapmak gereksiz karmaşa.
Global client state isAuthenticated, user, isHydrating Zustand (src/stores/, M12) Sunucudan türetilmiş ama uygulamanın her yerinde anında lazım olan az sayıda bilgi.

Sepet neden Zustand'da değil? Çünkü sepetin gerçek sahibi backend: stok bitebilir, fiyat değişebilir (CartItemDto.priceChanged alanı tam da bunun için var), kupon sunucuda doğrulanır, kullanıcı web'den bir şey ekleyebilir. Sepeti Zustand'da tutarsan bu bilgilerin hiçbirini göremezsin. Sepet = sunucu state = TanStack Query. Zustand'ın sepetle tek ilgisi olmamalı.

Kendi kodunu açıkla

1. refreshPromise neden modül seviyesinde bir değişken?

let refreshPromise: Promise<string | null> | null = null;

Ana sayfa açıldığında aynı anda 3 istek gidip üçü birden 401 alabilir. Bu değişken olmasaydı üçü de ayrı ayrı refresh denerdi. API'nin refresh token'ı rotasyonlu olduğu için ilk refresh eski token'ı geçersiz kılar; ikinci ve üçüncü denemeler "geçersiz refresh token" alır ve kullanıcı sebepsiz yere logout olur. Modül seviyesindeki bu değişken, eşzamanlı refresh'leri tek bir çağrıda toplar.

2. Refresh isteği neden apiRequest ile atılmıyor?

Çünkü apiRequest, 401 gördüğünde refresh dener. Refresh isteğini de oradan atarsan ve o istek 401 alırsa, kendi kendini çağıran sonsuz bir döngü oluşur. Bu yüzden refresh her zaman "çıplak" fetch ile atılır.

Her isteğe token eklemek gereksiz (ve misafir akışında zararlı) olurdu. Bu bayrak, sözleşmedeki security: Bearer alanının koddaki karşılığı. M13'te sepet çağrılarını yazarken bu bayrağın nasıl ayarlanacağına özellikle dikkat edeceksin.

4. if (res.status === 204) return undefined as T; satırı neden var?

DELETE gibi uçlar gövdesiz cevap döner. res.json() çağırırsan boş gövdede parse hatası alırsın.

Neden AsyncStorage değil SecureStore?

AsyncStorage diske düz metin yazar; cihaza fiziksel erişimi olan biri veya rootlanmış bir cihazdaki başka bir uygulama okuyabilir. SecureStore iOS'ta Keychain'i, Android'de Keystore'u kullanır — işletim sisteminin şifreli, izole alanları. Token gibi veriler için fark önemlidir.

Bu fazda bilinçli olarak eksik bırakılanlar: istek zaman aşımı (AbortController), çevrimdışı algılama, ngrok header'ı ve hata mesajlarının kullanıcıya nasıl gösterileceği. Hepsi M18'de, gerçek ekranlarla test edebileceğin noktada eklenecek. Şimdi eklersen ne yaptığını göremeden yazmış olursun.

queryKeys.products({ page: 1, categoryId: 3 })
// ["products", { page: 1, categoryId: 3 }]  -> ayri cache girdisi

queryKeys.products({ page: 1, categoryId: 7 })
// ["products", { page: 1, categoryId: 7 }]  -> bambaska bir cache girdisi

1. Sayı ve fiyat formatı

Sözleşmedeki tuzak 1'i hatırla: fiyatlar number | string. Bu dönüşümü ekranlarda değil, tek bir yerde yap.

// src/lib/utils/format.ts

/** API sayilari "number | string" olarak dondurebiliyor; her zaman buradan gecir. */
export function toNumber(value: number | string | null | undefined): number {
  if (value === null || value === undefined) return 0;
  const n = typeof value === "number" ? value : Number(value);
  return Number.isFinite(n) ? n : 0;
}

const priceFormatter = new Intl.NumberFormat("tr-TR", {
  style: "currency",
  currency: "TRY",
  minimumFractionDigits: 2,
});

export function formatPrice(value: number | string | null | undefined): string {
  return priceFormatter.format(toNumber(value));   // 149.9 -> "149,90 TL"
}

const dateFormatter = new Intl.DateTimeFormat("tr-TR", {
  day: "2-digit",
  month: "long",
  year: "numeric",
});

export function formatDate(iso: string | null | undefined): string {
  if (!iso) return "";
  return dateFormatter.format(new Date(iso));
}

/** Indirim yuzdesi: 100 -> 75 ise %25 */
export function discountPercent(
  price: number | string,
  effectivePrice: number | string,
): number | null {
  const p = toNumber(price);
  const e = toNumber(effectivePrice);
  if (p <= 0 || e >= p) return null;
  return Math.round(((p - e) / p) * 100);
}

2. Sonsuz kaydırma hook'u

// src/hooks/use-infinite-products.ts
import { useInfiniteQuery } from "@tanstack/react-query";
import { getProducts, type ProductFilters } from "@/lib/api/product";
import { queryKeys } from "@/lib/api/query-keys";
import { toNumber } from "@/lib/utils/format";

const PAGE_SIZE = 20;

export function useInfiniteProducts(filters: Omit<ProductFilters, "page">) {
  return useInfiniteQuery({
    queryKey: queryKeys.products(filters),
    queryFn: ({ pageParam }) =>
      getProducts({ ...filters, page: pageParam, pageSize: PAGE_SIZE }),
    initialPageParam: 1,
    getNextPageParam: (lastPage, allPages) => {
      // Sozlesmede hasNext opsiyonel; varsa ona guven.
      if (lastPage.hasNext === false) return undefined;
      if (lastPage.hasNext === true) return allPages.length + 1;

      // Yoksa toplam sayidan hesapla.
      const loaded = allPages.reduce((sum, p) => sum + p.items.length, 0);
      return loaded < toNumber(lastPage.totalCount) ? allPages.length + 1 : undefined;
    },
  });
}

useInfiniteQuery neden useQuery değil? useQuery tek bir sonucu cache'ler — ikinci sayfayı çektiğinde birincinin üzerine yazar. useInfiniteQuery, sayfaları data.pages dizisinde biriktirir. Ekranda tek bir listeye çevirmek için düzleştirirsin:

const products = data?.pages.flatMap((page) => page.items) ?? [];

getNextPageParam undefined döndürdüğünde "sayfa kalmadı" demektir; hasNextPage otomatik false olur.

4. Filtreler — ve neden reset kodu yazmıyorsun

1. Debounce hook'u

// src/hooks/use-debounced-value.ts
import { useEffect, useState } from "react";

export function useDebouncedValue<T>(value: T, delayMs = 300): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(timer);   // her yeni tusta oncekini iptal et
  }, [value, delayMs]);

  return debounced;
}

Debounce neden gerekli? "kitap" yazan kullanıcı için 5 tuş = 5 istek demek. Bu sadece trafik israfı değil, aynı zamanda yarış durumu yaratır: "kit" için gönderilen istek, "kitap" isteğinden sonra dönerse ekranda yanlış sonuçlar kalır. useEffect'in temizleme fonksiyonu (clearTimeout) her yeni tuşta önceki zamanlayıcıyı iptal eder; kullanıcı yazmayı bıraktıktan 300ms sonra tek bir istek gider.

Ek koruma: TanStack Query, queryKey'de arama terimi olduğu için geç dönen eski cevabı zaten yeni key'e yazmaz. Debounce + query key birlikte yarış durumunu tamamen kapatır.

  if (error instanceof ApiError && error.problem?.errors) {
    return Object.fromEntries(
      Object.entries(error.problem.errors).map(([field, messages]) => [
        field.charAt(0).toLowerCase() + field.slice(1),  // "Email" -> "email"
        messages[0],
      ]),
    );
  }
  return {};
}

export function getErrorMessage(error: unknown): string {
  if (error instanceof ApiError) return error.message;
  return "Beklenmeyen bir hata olustu.";
}

5. Optimistic update — ikinci adım olarak

Basit sürüm çalıştıktan sonra buraya gel. Optimistic update, sunucu cevabını beklemeden arayüzü güncelleyip anında tepki vermektir. Adet artırma butonunda hissedilir fark yaratır.

export function useUpdateCartItem() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: ({ productId, quantity }: { productId: number; quantity: number }) =>
      updateCartItem(productId, quantity),

    onMutate: async ({ productId, quantity }) => {
      // 1) Ucusta olan sepet sorgularini durdur ki cevaplari bizi ezmesin
      await queryClient.cancelQueries({ queryKey: queryKeys.cart });
      // 2) Mevcut hali sakla (geri alma icin)
      const previous = queryClient.getQueryData<Cart>(queryKeys.cart);
      // 3) Arayuzu simdiden guncelle
      queryClient.setQueryData<Cart>(queryKeys.cart, (old) =>
        old
          ? {
              ...old,
              items: old.items.map((i) =>
                Number(i.productId) === productId ? { ...i, quantity } : i,
              ),
            }
          : old,
      );
      return { previous };
    },

    onError: (_err, _vars, context) => {
      if (context?.previous) {
        queryClient.setQueryData(queryKeys.cart, context.previous);  // geri al
      }
    },

    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: queryKeys.cart });   // gercekle esitle
    },
  });
}

Üç kanca, üç görev: onMutate iyimser değişikliği yapar ve eski hali saklar; onError geri alır; onSettled (başarı da hata da olsa) sunucuyla eşitler. onError'daki geri almayı yazmazsan kullanıcı "eklendi" görür ama sunucuda hiçbir şey olmamıştır — bu, optimistic update'in en tehlikeli hatasıdır.

Neden ara toplam güncellenmiyor? Çünkü onu sunucu hesaplıyor. Optimistic olarak sadece kullanıcının doğrudan değiştirdiği alanı (adet) güncelle; para hesabını sunucuya bırak, onSettled nasılsa gerçeği getirecek.

      queryClient.invalidateQueries({ queryKey: queryKeys.favoriteIds });
      queryClient.invalidateQueries({ queryKey: queryKeys.favorites });
    },
  });

  return { isFavorite, toggle: mutation.mutate, isPending: mutation.isPending };
}

Şimdi M9'daki iskeleti değiştir — sadece iki satır:

export function FavoriteButton({ productId }: { productId: number }) {
  const { isFavorite, toggle, isPending } = useFavoriteToggle(productId);
  // ...gerisi ayni
}

İki query'yi de invalidate etmek şart. Sadece favoriteIds'i tazelersen, "Favorilerim" ekranı silinmiş ürünü göstermeye devam eder.

Misafir kullanıcı favoriye basarsa? Favori uçları Bearer istiyor. Ya butonu misafirde gizle, ya da dokunulduğunda giriş ekranına yönlendir. Sessizce 401 alıp hiçbir şey olmaması, kullanıcının anlamadığı bir "bozukluk"tur.

Sipariş oluşturma ve Idempotency-Key

npx expo install expo-crypto
// src/lib/api/order.ts
import * as Crypto from "expo-crypto";
import type { OrderDetail } from "@/types/dto";
import { apiRequest } from "./client";

type CreateOrderRequest = {
  addressId: number;
  note?: string | null;
  expectedTotal?: number | null;
};

export function createOrder(payload: CreateOrderRequest, idempotencyKey: string) {
  return apiRequest<OrderDetail>("/api/orders", {
    method: "POST",
    auth: true,
    body: payload,
    headers: { "Idempotency-Key": idempotencyKey },
  });
}

export function newIdempotencyKey() {
  return Crypto.randomUUID();   // senkron, UUID v4
}

Idempotency-Key neden gerekli? Kullanıcı "Siparişi Tamamla"ya bastı, istek gitti, ama cevap gelmeden bağlantı koptu. Uygulama başarısız sandı, kullanıcı tekrar bastı. Sunucuda iki sipariş oluştu. Bu anahtar, sunucuya "bu anahtarla daha önce bir sipariş oluşturduysan yenisini yapma, öncekini döndür" der.

Butonu disable etmek neden yetmiyor? Disable etmek yalnızca arayüz katmanında çift dokunuşu engeller. Uygulama kapanıp açılırsa, ya da mutation retry'ı devreye girerse o koruma yok olur. Idempotency-Key sunucu tarafında garanti veren asıl mekanizmadır; buton kilidi sadece ek bir konfor katmanı.

Anahtarın ömrü kritik: Aynı sipariş denemesi boyunca aynı anahtar kullanılmalı. Her render'da yeni UUID üretirsen koruma tamamen anlamsızlaşır.

// Checkout ozet ekraninda
const idempotencyKey = useRef(newIdempotencyKey());   // ekran acildiginda bir kez

const { mutate, isPending } = useMutation({
  mutationFn: () => createOrder({ addressId }, idempotencyKey.current),
  retry: false,                       // siparis olusturmayi ASLA otomatik tekrarlama
  onSuccess: (order) => {
    queryClient.invalidateQueries({ queryKey: queryKeys.cart });
    router.replace(`/checkout/payment?orderNumber=${order.orderNumber}`);
  },
});

// Kullanici odemeyi iptal edip yeniden denerse yeni bir deneme baslar:
const restart = () => { idempotencyKey.current = newIdempotencyKey(); };
  • retry: false — mutation'lar varsayılan olarak tekrar denemez ama açıkça yazmak, sonradan biri global ayar değiştirdiğinde seni korur.
  • CreateOrderRequest.expectedTotal alanı var: sepet toplamını gönderirsen sunucu, arada fiyat değiştiyse siparişi reddedebilir. Kullanıcıyı beklenmedik tutardan korur.
  • 409 Conflict gelirse (stok bitti, fiyat değişti) kullanıcıya anlaşılır bir mesaj göster ve sepete geri gönder — ham hata metnini basma.

// src/app/checkout/payment.tsx (ozet)
import { WebView } from "react-native-webview";

export default function PaymentScreen() {
  const { orderNumber } = useLocalSearchParams<{ orderNumber: string }>();
  const { data, isLoading, isError, refetch } = usePaymentInit(orderNumber);
  const [checking, setChecking] = useState(false);

  if (isLoading) return <LoadingState label="Odeme sayfasi hazirlaniyor..." />;
  if (isError || !data) return <ErrorState onRetry={refetch} />;

  return (
    <WebView
      originWhitelist={["*"]}
      source={{ html: data.checkoutContent }}
      onNavigationStateChange={(navState) => {
        // Yonlendirme yalnizca bir SINYAL: "muhtemelen bitti, simdi dogrula"
        if (navState.url.includes("payment-success") || navState.url.includes("payment-fail")) {

          router.replace(`/checkout/result?orderNumber=${orderNumber}`);
        }
      }}
      startInLoadingState
    />

Neden WebView'daki yönlendirmeye güvenmiyoruz? WebView içindeki URL değişimi istemci tarafında olur ve manipüle edilebilir. Ödemenin gerçekten alınıp alınmadığının tek doğru kaynağı backend'dir. Yönlendirmeyi sadece "sorgulamaya başla" sinyali olarak kullan, kesin sonucu GET /api/payments/{orderNumber}/status'tan al.

Sonuç ekranı, durum kesinleşene kadar kısa aralıklarla sorgular. TanStack Query bunu refetchInterval ile hazır veriyor:

export function usePaymentStatus(orderNumber: string) {
  return useQuery({
    queryKey: ["payment-status", orderNumber],
    queryFn: () => getPaymentStatus(orderNumber),
    enabled: Boolean(orderNumber),
    refetchInterval: (query) => {
      const status = query.state.data?.status;
      // Sonuclanmadiysa 3 sn'de bir tekrar sor; sonuclandiysa dur.
      return status === "Pending" || status === undefined ? 3000 : false;
    },
  });
}

Sonsuza kadar sorgulamasın: 60 saniye sonra "Ödemeniz işleniyor, siparişlerinizden takip edebilirsiniz" deyip siparişler ekranına yönlendir.

İptal butonunu ne zaman göstermeli?

API yalnızca Pending ve Paid durumundaki siparişlerin iptaline izin veriyor. Bu kuralı arayüzde de uygula:

const canCancel = order.status === "Pending" || order.status === "Paid";

{canCancel ? <CancelOrderButton orderNumber={order.orderNumber} /> : null}

"Backend zaten kontrol ediyor, arayüzde tekrar etmeye gerek yok" neden yanlış? İki kontrolün amacı farklı. Backend veri bütünlüğü ve güvenlik için kuralı her zaman uygulamalı — arayüze asla güvenemez. Arayüz ise kullanıcıya anlamsız bir aksiyon göstermemek için aynı kuralı uygular. Biri diğerinin yerine geçmez: backend kontrolü olmadan sistem savunmasız, arayüz kontrolü olmadan kullanıcı deneyimi kötü olur.

İptal bir mutation; başarılı olunca hem listeyi hem detayı invalidate et. Onay için mutlaka bir doğrulama penceresi göster (Alert.alert yeterli) — geri alınamaz aksiyonlar tek dokunuşla olmamalı.

onSuccess: () => {
  queryClient.invalidateQueries({ queryKey: ["orders"] });          // tum sayfalar
  queryClient.invalidateQueries({ queryKey: queryKeys.order(orderNumber) });
},

["orders"] ile kısmi eşleşme kullandık: sayfalı listenin tüm filtre/sayfa kombinasyonları tek seferde bayatlar.

M2'de bilinçli olarak ertelediğimiz şeyler burada. Artık gerçek ekranların var, yani ne yaptığını görerek ekleyebilirsin.

1. İstek zaman aşımı

// src/lib/api/client.ts icinde rawRequest'e ekleme
async function rawRequest(path: string, options: RequestOptions, token?: string | null) {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), 15000);   // 15 sn

  try {
    return await fetch(`${BASE_URL}${path}`, {
      method: options.method ?? "GET",
      headers: { /* ... */ },
      body: options.body ? JSON.stringify(options.body) : undefined,
      signal: controller.signal,
    });
  } finally {
    clearTimeout(timeout);
  }
}

Zaman aşımı olmadan, sunucu cevap vermediğinde kullanıcı sonsuza kadar dönen bir gösterge izler. Mobil ağlarda bu sık olur.

2. Hataları sınıflandır

Kullanıcı için "sunucu hatası" ile "internet yok" farklı şeylerdir; farklı çözümleri vardır.

export class NetworkError extends Error {
  constructor(public cause?: unknown) {
    super("Baglanti kurulamadi");
  }
}

// apiRequest icinde
try {
  res = await rawRequest(path, options, token);
} catch (err) {
  // fetch yalnizca AG hatasinda throw eder; 500 bile throw etmez
  throw new NetworkError(err);
}
// states.tsx icinde kullanim
export function QueryErrorState({ error, onRetry }: { error: unknown; onRetry: () => void }) {
  const isOffline = error instanceof NetworkError;
  return (
    <ErrorState
      message={isOffline ? "Internet baglantinizi kontrol edin" : "Bir seyler ters gitti"}
      onRetry={onRetry}
    />
  );
}

Bilmen gereken: fetch yalnızca ağa hiç ulaşamadığında istisna fırlatır. 404, 500 gibi durumlar "başarılı" bir cevaptır — bu yüzden client.ts'te res.ok kontrolü var. Web'den gelenlerin en sık şaşırdığı davranış budur.

3. Başarı geri bildirimi

"Sepete eklendi" gibi anlık bildirimler için basit bir toast yeter. Ekstra paket kurmadan, kök layout'ta bir Animated.View ve küçük bir Zustand store'u ile yazabilirsin (bu, Zustand'ın doğru kullanım alanına ikinci bir örnek: geçici, global, sunucudan gelmeyen UI state).

4. Gözden geçirme turu

Yazdığın her ekranı aç ve sekiz durumu tek tek dene. En kolay yöntem: uçak modu, sonra .env'deki URL'i geçici olarak bozmak, sonra backend'i durdurmak.
